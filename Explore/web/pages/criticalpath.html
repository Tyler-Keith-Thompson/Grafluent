Critical path

Some tasks have to wait for others. How soon can the whole project be done, and which tasks can’t slip?

Example: putting on a school play. Each task takes some days, and an arrow means the task at its tail must be finished before the next can start. Tasks with no arrow between them can run at the same time.

In SwiftThe play above, in Grafluent







  
The ideaThe longest path sets the pace

  
The tasks and their arrows form a directed graph with no cycles: a task can’t wait for itself. Take the tasks in a topological order, so everything a task waits for comes first, and give each the earliest start it can have: the latest finish among the tasks it waits for. One pass in that order schedules everything, in time proportional to the tasks plus the arrows.

  
The project’s length is then the longest path through the graph, counting each task’s days. The tasks on it are the critical path: each starts the moment the one before it ends, so a day lost on any of them is a day lost on the opening. Every other task has slack, found by a second pass backwards from the end: the latest it can start is the earliest any task after it must start, less its own days.

  
Longest paths are hard in general graphs, but easy here: without cycles, there is no way to go round and round making a path longer. longestPath(weight:) on a DirectedAcyclicGraph runs the same pass over the order it already keeps. The weight here is the days of the task an arrow leaves, so the path’s weight is the total of its tasks.


  
Where it breaksDurations are guesses, and people are limited

  
The critical path assumes every task takes exactly its estimate. Real tasks vary, and a path with a little slack can turn critical when one of its tasks runs late; PERT treats each duration as a range and asks how likely the deadline is. It also assumes unlimited hands: if the same three people must build the set and make the costumes, those tasks can’t overlap, and scheduling with limited resources is a much harder problem.

  
If the arrows ever form a cycle, no order exists at all: DirectedAcyclicGraph refuses the edge that would close it, and findCycle() on a plain graph shows which tasks wait for each other.
