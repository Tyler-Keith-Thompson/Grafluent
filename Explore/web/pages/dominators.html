Dominators

Say itLENG-ow-er TAR-jun/ˈlɛŋaʊ̯ɐ ˈtɑːrdʒən/

Which parts of a program are sure to have run by the time it reaches a given line?

Example: a function that adds up the numbers in a file, line by line, warning about lines that aren’t numbers and giving up after too many. Each block is a run of code with no jumps in it; the arrows are the jumps. A block dominates another when every path from the entry to the second passes through the first.

func total(of lines: [String]) throws -> Int {
    var sum = 0, bad = 0, count = 0            // entry
    for line in lines {                        // loop
        if let n = Int(line) {                 // check
            sum += n                           // add
        } else {
            bad += 1                           // warn
            if bad > 3 { throw TooManyBad() }  // give up
        }
        count += 1                             // next
    }
    return sum                                 // done
}                                              // exit

The ideaThe blocks you can’t get around

  
Each block has a chain of dominators running back to the entry, and the nearest one is its immediate dominator. Every block but the entry has exactly one, so drawing each block under its immediate dominator gives a tree: the dominator tree. A block’s ancestors in that tree are exactly the blocks that dominate it, which is why dominates(_:_:) answers in constant time once the tree is built.

  
The check in the second lab follows the definition: take a block out, search from the entry, and whatever is cut off is what that block dominates. That is one search per block. Lengauer and Tarjan get every immediate dominator from a single depth-first search. Each block first gets a semidominator: the earliest block in the search’s order with a path to it that detours only through later blocks. One more pass over the search tree turns semidominators into immediate dominators. Grafluent’s dominatorTree(root:) runs that algorithm, in time close to linear in the number of jumps.

  
Turn every arrow around and ask from the exit instead, and you get post-dominators: the blocks sure to run after a given one, from postDominatorTree(exit:). Compilers use both. A loop’s head dominates its body, which is how loops are found; and the dominance frontier, where one block’s dominance stops, is where a variable assigned in two branches needs a merge, which dominanceFrontiers(root:) lists.


  
Where it breaksCode nothing reaches, and code that never ends

  
A block the entry can’t reach has no dominators at all: “every path passes through” is vacuous when there is no path. Grafluent answers nil from dominators(of:) for such a block, rather than an empty list, so dead code can’t be mistaken for code with no requirements. Post-dominators have the same gap from the other end: a block that loops forever, or a function with two exits, never reaches the one exit you named. Give every exit a jump to one shared exit block first.

  
Dominance is about the jumps as drawn, not about the values that choose between them. Here give up only ever follows several warnings, but the graph sees one arrow from warn and no count. What dominators promise holds on every path through the graph, which is why a compiler can rely on them; facts that depend on the data are beyond them.
