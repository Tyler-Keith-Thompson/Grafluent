Changing a stored graph

How can a graph keep changing without losing the speed of packed arrays?

What it’s forGraphs that change all the time

Most real graphs are never finished. People follow and unfollow. Servers come and go. A route map gets a new road every week. The algorithms that run on these graphs want each vertex’s neighbours packed side by side in memory, because a processor reads a packed row very fast. Compressed sparse row stores the rows that way, but it can’t take a new edge without a rebuild. An adjacency list takes new edges all day, but its rows drift apart as they grow, and walking them slows down.

Packed rows keep both. Every row stays packed, in order, with a few spare cells after it. Adding an edge usually fills a spare cell. When a row runs out, a small neighbourhood of rows is laid out again to share the spare cells around. Walking the graph reads one array from start to end, as compressed sparse row does. Reach for PackedCompressedSparseRow when a graph changes between the times you run algorithms on it, and you run them often.

Compared withThree ways to store a changing graph

If you only add edges and seldom walk the whole graph, the adjacency list is simpler and quicker to build. If you walk it often between changes, packed rows pay back the extra cost of each insert many times over.

Example: six people and who follows whom, with the storage drawn underneath. It starts built in one go, so the rows are packed tight. Add one follow and watch the storage spread out with spare cells. Keep adding and most follows drop into a spare cell. Fill it up and the whole storage doubles.

The ideaA bookshelf with gaps

Think of a bookshelf where each person’s books stand together, with a little empty space after each run. A new book usually slides into that space. When one run has no space left, you look at the shortest stretch of shelf around it. If that stretch is not too full, you spread its books out again so every run gets some space. If it is too full, you take a longer stretch, and longer again. Only when the whole shelf is more than seven tenths full do you buy a shelf twice as long.

Packed rows do exactly that with cells. A short stretch may be up to 92 percent full before it is spread out again. The whole storage may only be 70 percent full. The thresholds fall from one to the other, so a spread at any size leaves its rows room to grow before they ask again. That is a packed memory array, and the structure is the packed compressed sparse row of Wheatman and Xu. Each insert moves O(log² n) cells on average, and every walk reads the storage once, forward.

Edges keep their positions through all of it. A rebalance moves cells, never the number an edge goes by, so anything attached to the edges, a weight or a label, stays where it is.

Where it breaksAdding at the end, over and over

The spare cells are spread out evenly, but a stream of inserts that all land in the same place uses them up there first. Adding vertices one after another, each with its edges, always hits the newest row at the end of the storage. The end fills, spreads, fills again, and each spread is larger than the last. It still works, but each insert costs more than on a graph whose inserts land anywhere. If that is your pattern, build with an adjacency list and convert once, or build in one go.

Removing an edge is cheap: the row’s last entry moves into the hole, and the cell is spare again. When fewer than a quarter of the cells are in use, the storage halves, so memory follows the graph down as well as up.
