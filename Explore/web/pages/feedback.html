Feedback sets

Nine packages import each other in four loops, so nothing can be built first. What is the smallest number of imports to cut, and which?

What it’s forBreaking every loop at the least cost

An arc is a directed edge, an arrow. A feedback arc set is a set of arrows whose removal leaves no directed cycle; a feedback vertex set does the same with vertices. The minimum ones are the cheapest way to make a graph acyclic: the fewest imports to untangle, the fewest tables to drop from a chain of foreign keys, the fewest matches to discount when ranking teams from who beat whom, or which edges must point upward when drawing a graph in layers.

Both minimum problems are NP-hard, so the exact answers take time that doubles with each extra vertex and are for small graphs: a dependency graph of a few dozen packages, not a web crawl. For large graphs there is a fast heuristic that is usually close.

Compared withWays to get rid of cycles

Take the exact set when the graph is small and the count matters; take the heuristic otherwise. A condensation keeps the loops and works around them.

Example: nine packages whose imports form four loops: tests that import the app and the app that imports its tests, a cache behind an auth package behind a database behind the cache, and a logger that imports the core that imports it, with a detour through the network package.

Step throughOne cut a step

The ideaOrder the vertices, then count the arrows pointing backward

Write the vertices in a line. Every arrow then points forward or backward, and the backward ones are a feedback arc set: remove them and every remaining arrow points forward, so no cycle can close. Every feedback arc set arises this way from some order, so the minimum one is the order with the fewest backward arrows. minimumFeedbackArcSet() finds that order by dynamic programming over subsets of vertices, solving every smaller set of vertices first and reusing those answers: the best order of a subset ends with the vertex whose arrows into the rest cost least, after the best order of the rest. Each subset is one entry in a table with 2ⁿ rows, which is why the search stops at 28 vertices. The weighted form adds up weights instead of counting, and a self-loop is always in the set, since no order can point it forward.

minimumFeedbackVertexSet() fills a table of the same size with a yes or no: a subset of vertices induces an acyclic subgraph, meaning the vertices and only the arrows between them have no cycle, when one of its vertices has no arrow coming in from the subset and the rest is acyclic, peeled one source, a vertex with no arrows in, at a time. The largest acyclic subset is everything not in the answer; on an undirected graph the peeling takes vertices with at most one neighbour left and finds the fewest vertices leaving no cycles, a forest of trees.

feedbackArcSet() is Eades, Lin and Smyth’s heuristic: it builds an order greedily, placing sinks, vertices with no arrows out, at the end and sources at the start and otherwise the vertex with the most arrows out relative to in, and takes the backward arrows of that order.

Where it breaksThe table doubles with every vertex

Thirty vertices would need a table of a billion rows, so the exact searches stop at 28 and 32, and stop the program with an error beyond that. On a bigger graph, condense it first: only the strongly connected pieces hold cycles, and each piece can be solved on its own if it is small enough. The heuristic has no such limit but no promise either; on this example it matches the minimum, and on others it can take a few more arrows than needed. And when several minimum sets exist, which arrows the exact search returns is unspecified, and the vertex search returns the minimum set that comes first in vertex order.
